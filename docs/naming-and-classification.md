# 命名与分类判据

本规范给出公开、可移植的命名和分类判据，供 Agent 生成或审阅索引记录时使用。它不授予访问、移动或删除权限；示例均为合成名称或占位符，不含机器真实路径、账户、目录清单、会话记录或凭据。

## 1. 命名规范

### 1.1 通用字符集与编码

- 目录名和文件名使用 UTF-8；显示名称统一采用 Unicode NFC。
- 允许字母、数字、空格、下划线、连字符和点；点只用于扩展名、版本分隔或明确约定的标识，不以点开头或结尾。
- 禁止控制字符、未配对的代理项、路径分隔符出现在单个名称中，禁止纯空白、`.`、`..` 和宿主保留设备名。
- 禁止 `< > : " / \\ | ? *` 作为跨平台可移植名称中的字面字符；宿主允许也不得把它们写入公开示例或可交换索引。
- 单个名称建议不超过 80 个 Unicode 字符，完整路径段建议不超过 180 个字符；超限时先缩短语义名称，不截断扩展名或校验值。
- Windows 宿主默认不依赖大小写区分身份；同一范围内不得仅靠大小写创建并列名称。macOS 归一化差异也按冲突处理。

### 1.2 大小写、分隔与可读性

- 目录角色名优先 `kebab-case`；代码包、模块和库按其语言既有约定，不因整理而重命名。
- 人类可读名称优先空格或连字符；机器稳定标识优先小写连字符或下划线，不混用多种约定。
- 名称应表达用途而不是整理时间；避免 `new`、`old`、`final`、`misc`、`stuff` 等没有责任或生命周期含义的词。
- 同一批次内同类对象使用同一模板；模板变更须记录生效时间和迁移规则。

### 1.3 日期、版本与序号

- 日历日期使用 `YYYY-MM-DD`，时间戳使用 ISO 8601 UTC；不得使用两位年份或本地习惯造成歧义的纯数字。
- 版本使用 `v<major>.<minor>.<patch>` 或宿主既有语义版本；后缀顺序固定为 `<base>-<qualifier>-<date-or-sequence>`。
- 消歧序号使用固定宽度（如 `-01`、`-02`），不得用「最终版」「真正最终版」；已有目标冲突时进入 hold，不覆盖。
- 归档目录可用 `-archive-YYYY` 或 `archive/YYYY/YYYY-MM-DD` 后缀；后缀只说明封存批次，不证明内容用途、可删除性或权威性。
- 摘要、事务 ID 和操作 ID 作为不透明标识，不在名称里截断、重新编码或拼接秘密值。

### 1.4 保留名、异常名与改名

- 应用、版本控制、包管理器、数据库、虚拟机、服务或系统管理的名称保持不动；其含义由对应所有者解释。
- 畸形名、空名称、过长名、控制字符名、重名归一化冲突进入 `UNRESOLVED_HOLD`，先记录稳定引用和数字摘要，再向责任方确认。
- 改名属于变更事务：dry-run 列出旧/新引用、碰撞、引用更新范围、验证方法、备份与回滚；不覆盖目标，不把改名当作分类结论。
- 国际化名称保留原字符，另以索引字段记录检索别名；别名不得改变权威名称或自动产生第二份正文。

## 2. 分轴分类

分类结论至少包含 owner、role、privacy、lifecycle、confidence 五轴、`updated_at`、有限证据和适用 Schema 版本。文件名、大小、修改时间、哈希都只是证据之一；任何单轴都不能证明可删除性、授权或权威性。

### 2.1 默认值与证据门槛

默认结论永远是 `unknown / unknown / unknown / hold / low`，并附一条「为什么不升级」的证据说明。升级为 `high` 至少满足：有明确所有者或用户说明；用途与目录上下文、版本控制状态、格式元数据或生成规则一致；隐私边界明确；无未解释冲突。`medium` 表示证据一致但缺少责任方确认；`low` 表示只有名称、时间或单一启发式。

证据须是可复核的有限描述：任务授权、目录职责登记、清单条目、版本控制状态、格式/魔数、应用所有权标记、内容摘要、用户说明。不得记录凭据值、敏感正文或不必要的个人数据；受限证据只保留 opaque 引用、算法和摘要。

### 2.2 owner：谁负责

| 值 | 可操作判据 | 默认与冲突 |
| --- | --- | --- |
| personal | 用户明确说明由个人维护，且不属于项目/应用/系统目录 | 仅凭用户名目录不够 |
| system | 操作系统、驱动、固件或平台自带结构登记 | 不因路径像系统目录而移动 |
| application | 应用安装、配置、缓存、数据库或包管理器目录由其自身管理 | 与 project 冲突时优先应用所有权，进入 hold |
| project | 明确属于已登记项目、版本控制工作树或项目交付物 | 需项目入口或清单证据 |
| team | 组织/团队责任方登记，且有共享维护规则 | 无责任方时 unknown |
| external | 第三方、客户或外部来源明确提供 | 许可和保留条件另记，不推定可发布 |
| unknown | 以上证据缺失或互相冲突 | 默认；保护但不猜测 |

### 2.3 role：在工作流中的作用

| 值 | 可操作判据 | 默认与冲突 |
| --- | --- | --- |
| source | 可编辑原始输入、源码、配置源或创作源，且被当前工作依赖 | 源码和生成物分开记录 |
| active_work | 当前任务或当前周期内正在编辑、运行或审阅 | 仅凭 mtime 不判定 |
| reference | 只读查阅、规范、样本、合同或外部资料 | 不自动归档 |
| generated | 可由声明的工具、输入和规则重建 | 需生成规则或目录约定证据 |
| application_state | 应用自有状态、数据库、缓存、会话或锁 | 默认不动 |
| cache | 可丢弃但运行时可能依赖的加速数据 | 哈希相同不等于可删 |
| archive | 按时间点封存、明确不再常规修改的历史批次 | 需封存时间和保留类别 |
| inbox | 收取但未分类、等待责任方处置的入口 | 不等于临时垃圾 |
| temporary | 有明确创建者、用途和到期条件的短生命周期数据 | 过期不自动删除 |
| backup | 为恢复保留、带来源代次和验证状态 | 不因可读或较新成为权威 |
| unknown | 作用不明或证据冲突 | 默认 |

### 2.4 privacy：可读取、共享和发布的边界

| 值 | 可操作判据 | 默认与冲突 |
| --- | --- | --- |
| public | 已脱敏、经责任方批准公开，且不含真实机器路径、账户、清单、日志、会话或凭据 | 放在公开仓库不等于自动 public |
| internal | 本机或组织内部工程状态、路径映射、运行记录，不适合公开 | 二元宿主映射为受限 |
| restricted | 个人数据、完整目录清单、会话、真实 manifest、私有证据 | 按当前任务授权访问 |
| secret | 凭据、密钥、令牌、Cookie 或认证值 | 仅存 opaque 引用和本地保险库解析路径 |
| unknown | 未核验或分类证据冲突 | 默认按受限保护，不读正文、不外发 |

冲突时采用最严格可适用等级，并把 `confidence` 降到 `medium` 或 `low`；`secret` 与 `unknown` 均触发 hold，直至责任方给出边界。

### 2.5 lifecycle：是否仍在用与恢复条件

| 值 | 可操作判据 | 默认与冲突 |
| --- | --- | --- |
| active | 当前维护、服务或权威发布引用指向该对象 | 不因新近修改自动升级 |
| working | 有活动编辑或处理中事务，且未决状态明确 | 活动锁/事务结束时复核 |
| reference | 只读查阅，不承诺持续更新 | 需注明来源代次 |
| archive | 已封存并登记保留期限和恢复方式 | 与 active 冲突时 hold |
| rebuildable | 有可验证的输入、规则、工具版本和重建命令 | 只说明可重建，不说明可删除 |
| hold | 用途、所有权、隐私、冲突或真实结果未决 | 任何停止条件未满足时默认 |
| retired | 责任方批准停止使用，登记时间与替代项 | 不自动进入删除流程 |
| unknown | 生命周期证据缺失 | 默认 |

### 2.6 confidence：结论可信度

| 值 | 可操作判据 | 处理 |
| --- | --- | --- |
| high | 责任方、用途、边界、状态均有独立可复核证据且无冲突 | 可进入已授权 dry-run |
| medium | 证据一致但缺责任方确认，或只有两类间接证据 | 只做建议，不自动执行 |
| low | 名称启发式、单一元数据、旧快照或证据冲突 | 保持 hold，补充只读证据 |

## 3. 冲突消解优先级

1. 安全与隐私边界：更严格等级优先；`unknown` 默认受限；`secret` 只保留 opaque 引用。
2. 当前任务授权与宿主规则：超出范围、受限根、应用/系统所有权、外部服务和永久删除一律不自动推进。
3. 责任方明确说明与正式登记：登记索引、用户说明、应用入口优先于路径猜测。
4. 可复核来源链与版本代次：来源身份、完整性、验证证据优先于修改时间、大小、路径顺序、哈希字典序或副本多数。
5. 直接证据优先于间接证据：内容/格式元数据与生成规则优先于文件名；多轴一致优先于单轴高分。
6. 仍有冲突：全部候选保留，标 `UNRESOLVED_HOLD`，附冲突摘要、稳定引用和升级对象；禁止合并冲突正文、禁止猜权威。

## 4. unknown 与 hold

`unknown` 是某一分类轴缺少可信结论；`hold` 是生命周期/执行状态，表示暂停推进。对象可以某个轴 high、另一个轴 unknown；只要 owner、role、privacy 或真实后置状态影响安全，整体就保持 hold。

进入条件：证据缺失；证据互相冲突；可能为应用/系统/受限数据；目标冲突；链接或挂载边界未核验；事务部分失败且结果未知；责任方或保留要求未定。

退出条件：补齐明确授权、责任方说明、目录职责登记、格式/版本控制证据、冲突裁决、完整性和验证结果；由有权维护者记录旧结论、新结论、理由、时间、证据引用与回滚条件。退出 hold 不等于获得删除、发布或迁移授权。

## 5. 记录模板

合成模板只演示字段语义，不对应真实对象：

```json
{
  "record_id": "synthetic-record-001",
  "item_ref": "fixture://authorized-root/example/item.txt",
  "item_kind": "file",
  "owner": "unknown",
  "role": "unknown",
  "privacy": "unknown",
  "lifecycle": "hold",
  "confidence": "low",
  "evidence": ["synthetic: no owner statement or directory-role registration"],
  "updated_at": "2026-01-01T00:00:00Z"
}
```

分类建议默认只输出 dry-run。任何写操作仍须经过有界事务、备份、碰撞检查、真实后置状态核验和回滚记录；schema 合法只证明数据形状，不证明上述事实。
