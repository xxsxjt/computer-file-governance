# 不向模型提供商暴露明文凭据

## 目的

本规范保护的是凭据不进入模型提供商可见的提示词、工具参数、工具结果、配置或日志；它不是用来防止 Agent 在本机调用用户授权的能力，也不以模型提供商是否“可信”作为单独拒绝理由。

## 调用方式

1. Agent 按用户授权发起正常操作，例如访问仓库、创建资源或推送已审核内容。工具参数只含完成操作所需的非凭据字段。
2. 本机 vault-backed adapter 在本机解析凭据，并直接用于目标服务的认证请求。凭据可以短暂存在于本机 adapter 的进程内存中；不返回给 Agent，也不要求 Agent 读取、粘贴或传递明文。
3. Adapter 返回完成操作所需的普通状态和结果。凭据值、Authorization header、解析输出及含凭据的调试信息不得进入模型可见内容、终端输出、Agent 配置或日志。
4. 操作仍遵循用户任务授权和已有工具正常的确认流程。仅因 Agent 所用的模型提供商不受信任，不应拒绝它调用已配置的本机 adapter。

## 可见性边界

- 模型提供商仍可见普通工具调用参数和返回内容，例如仓库名、文件内容、API 返回数据及操作状态。隐藏 Token 不会自动隐藏这些数据；仍按对应数据的隐私等级判断是否可发送给该模型。
- 目标服务会收到用于认证的凭据或认证头，这是 API/Git 操作成立所必需的传输；要求使用 HTTPS 等目标服务认可的安全通道。
- Adapter 使用已配置凭据，不会自动缩小其服务端权限范围。Token 的实际权限仍由 GitHub/vault 中的凭据设置决定。
- 本规范不声称能阻止恶意本机 Agent、同一用户下的进程或拥有本机权限的人使用本机能力；防止这类本机访问不属于本规范目标。
- 文档本身不会创建工具能力。目标 Agent 必须已配置可调用的本机 adapter；如果没有相应工具，就不能仅凭阅读本文件执行操作，也不应要求用户把 Token 粘贴给模型。

## Adapter 最小互操作合同

本仓库定义的是安全边界，不声称提供真实 vault、解锁器或服务连接。宿主实现若要宣称兼容，至少应满足以下合同：

1. **请求输入**：Agent 只能提交非秘密业务参数、目标服务/资源、允许的操作名称和 opaque credential reference。不得接受明文 Token、密码、Cookie、私钥或任意 URL 形式的“凭据值”。
2. **目标与操作限制**：adapter 在本机执行 service/target/operation allowlist；凭据属于哪个服务、允许哪些动作和资源范围必须可审计，不能因“已配置凭据”自动获得任意目标或任意 HTTP 能力。
3. **返回值**：返回稳定的状态、错误类别和完成操作所需的普通结果；凭据值、认证头、解析后的秘密字段、调试转储和可能重建秘密的内容必须被删除或脱敏。
4. **日志与审计**：日志只能记录最小 opaque 引用、目标类别、操作、时间、结果类别和 request/operation id；不得记录密钥值、解锁材料、完整认证请求或未经隐私评估的业务正文。
5. **失败关闭**：缺少引用、目标不在 allowlist、权限不足、vault 锁定、主机身份不明或响应无法脱敏时停止，不降级为要求用户把密钥粘贴给模型，也不自动改用任意 provider/endpoint。
6. **生命周期责任**：vault 所有者负责存储和访问策略；adapter 所有者负责解析、脱敏、超时、重试和审计；服务所有者负责权限、轮换和撤销。三者责任不能由本规范自动推断。
7. **部署声明**：只有在宿主配置完成并通过不含秘密的合同测试/金丝雀后，才能标记“已部署”；否则只能标记“规范已定义、部署未验证”。

## vault-adapter-v1 公共合同

公开仓库提供一个不连接保险库、不发起网络请求的合同校验器：
schemas/vault-adapter-contract.schema.json 与 lib/credential-contract.mjs。
它只校验合成请求/响应/审计/生命周期记录的形状和部分安全语义，不能证明真实引用存在、目标安全、权限成立或凭据没有在宿主其他输出通道泄露。

四类记录的职责固定如下：

| 记录 | 必须表达 | 明确禁止 |
| --- | --- | --- |
| request | contract/version、request id、service/target/operation、opaque credential 与 authorization 引用、受限业务参数、超时、幂等性、重试和强制审计 | 明文 Token、密码、Cookie、私钥、任意 URL/认证头 |
| response | request/run 关联、稳定状态、side-effect 状态、结果隐私等级、可返回结果或安全错误、脱敏状态、审计引用 | 凭据值、认证头、原始响应、未筛选异常和 outcome_unknown 的成功/失败假象 |
| audit | 最小 opaque 引用、时间、决策、结果类别、side-effect 状态、结果隐私、脱敏状态和重试次数 | 请求/响应正文、原始 URL、完整异常、密钥或可重建秘密 |
| lifecycle | vault/adapter/service 责任方、允许操作、引用模型、缓存策略、轮换复核时间、旧引用处置和撤销/缩权/事故事件 | 保险库路径、密文、解锁材料或未经授权的权限扩张 |

合同中的错误类别至少区分：请求/版本无效、引用不可用、策略/目标/操作拒绝、主机身份失败、认证/授权拒绝、超时、限流、服务不可用、响应无法安全筛选、审计不可用、内部错误和结果未知。
非幂等操作若允许多次尝试，必须带 idempotency: 引用；无法确认副作用或无法写入必要审计时必须保守返回 outcome_unknown，不得要求 Agent 读取或粘贴凭据。

validateVaultContract() 的字段名与合成材料扫描只是第一道门。宿主适配器仍须使用服务/操作专用的允许字段投影，覆盖返回值、异常、stdout/stderr、追踪和崩溃诊断；通用字符串替换不能替代允许字段投影。projectCredentialAuditEvent() 只生成最小审计投影，不复制业务结果或请求参数。

## GitHub 示例

Agent 需要访问 GitHub 时，向本机已配置的 GitHub adapter 提交仓库和操作参数。Adapter 在本机使用 vault-backed 凭据发起 GitHub API/Git 请求，再返回状态和必要结果。Agent 不获得 Token 字符串；模型提供商仍会看到 Agent 发送的仓库名、请求内容及 adapter 返回的普通数据。

文件治理任务中，提交 GitHub 前还要遵循核心 Skill：盘点待提交文件、检查隐私与凭据、验证目标内容和提交结果，并把机器专属目录清单、私人索引及实际 manifest 留在本机。

本仓库不得新增虚构的 vault export、凭据 CLI 或实际密钥样例来证明上述合同。真实保险库和 adapter 可以由宿主或其他受控工具提供，但其路径、密文和解锁材料不进入公开仓库。
