# 索引权威性与新鲜度规范

## 1. 目的与适用范围

本规范适用于治理索引、资产清单、引用目录及其派生记录。它规定权威判定、时效维护、重建发布、生命周期、留存和 Schema 演进；不授予访问受限数据、变更源系统或销毁数据的权限。所有操作仍须遵守适用的隐私边界、明确授权和保留要求。

“范围”指一组明确的对象、记录类型和治理角色；“代次”指一次完整生成并独立验证的索引版本；“来源修订”指可比较的上游版本号或事件序列。

## 2. Canonical authority 与副本

### 2.1 权威定义

Canonical authority（规范权威源）是针对已声明范围和角色，由指定责任方正式登记、负责维护，且能以来源链和验证证据识别的唯一当前事实来源。权威属于“范围—角色—登记来源”的关系，不由文件名、存放位置、访问权限、内容相似度或修改时间单独决定。

每个范围至少登记：稳定的范围标识、权威引用、责任方、允许的用途、适用 Schema 的 $id 与版本、隐私分类、生命周期、新鲜度 SLA、最后验证时间、验证证据引用及冲突升级对象。引用应采用可移植逻辑标识或已批准的定位方式；公开索引不得泄露机器专属位置或秘密值。

衍生索引可登记为该发布范围内的权威发布物，但须记录生成者、上游权威引用、来源修订/代次、生成与验证时间、验证结果和刷新期限。它不会因此取代上游系统对其原始数据的权威。

### 2.2 权威副本选择与冲突裁决

按以下顺序判断候选副本：

1. 查正式登记的 authority 引用、适用范围、角色和责任方。登记缺失或失效时，不得仅凭副本内容自行指定权威。
2. 核验来源身份和来源链、隐私/权限边界、范围覆盖、完整性及 Schema 合规性。
3. 核验可比较的来源修订、代次、验证证据和 SLA；时间戳仅是证据之一，不单独确立权威。
4. 登记来源相同且多个候选均有效时，选最新的已验证来源修订/代次。版本相同则按事先登记的确定性规则处理，未登记规则时交由责任方裁定。
5. 权威登记、来源链或内容冲突时标记 CONFLICT_HOLD，保留各候选和证据并升级处理。不得按文件时间、大小、路径顺序、哈希字典序或副本多数猜测，也不得拼合冲突内容。

内容哈希只证明指定时点的字节关系，不证明权威、正确、完整、当前或可删除。引用失效、越界或未验证的候选不得晋升为当前权威。

### 2.3 晋升、降级与合法副本

权威晋升须由范围责任方或其明确委派者批准，记录旧/新引用、适用范围、理由、来源与验证证据、生效代次、审批者、回滚条件。先完成候选核验，再更新发布引用并原子切换；失败时旧权威保持有效。镜像、备份、缓存、工作副本或重建结果不得自行晋升。

权威降级、撤销或替换由同一责任方或正式接任者批准。权威损坏、不可用或来源链断裂时标记 UNAVAILABLE 或 CONFLICT_HOLD，不得自动把备份改称权威。经批准的临时替代源须注明临时身份、权限、范围、到期/复核时间和回滚点。

合法副本按用途标注，至少采用以下角色之一：

| 角色 | 含义 | 使用限制 |
|---|---|---|
| CANONICAL | 登记的当前权威源 | 仅对登记范围有效 |
| PUBLISHED_DERIVATIVE | 从声明来源生成并验证的发布索引 | 仅在来源代次和 SLA 有效时作当前参考 |
| WORKING_COPY | 编辑或审阅副本 | 不得声称为已发布事实来源 |
| MIRROR | 为分发或可用性同步的副本 | 只读；记录方向、来源代次和同步滞后 |
| BACKUP / SNAPSHOT | 恢复用途或时间点副本 | 不因新近或可读而成为权威 |
| CACHE / DERIVED | 可重建的缓存或派生数据 | 记录规则与来源；过期时重算或弃用 |

每份副本记录角色、覆盖范围、authority 引用、来源代次/修订、创建与验证时间、验证结果、责任方、保留类别，以及适用时的摘要和同步方向。副本差异须依据用途和来源代次解释，不能一概视为错误。

## 3. 索引新鲜度与刷新

### 3.1 新鲜度等级

新鲜度表示索引对已声明来源的反映程度，不替代正确性、完整性或授权核验。

| 等级 | 标记 | 定义与处理 |
|---|---|---|
| 0 | CURRENT | 成功验证仍在 SLA 内，来源代次、完整性和 Schema 已核验。 |
| 1 | DUE_SOON | 未超 SLA，距刷新期限不超过该范围 SLA 的 20%；安排刷新。 |
| 2 | STALE | 已超 SLA，或已知来源变更而索引尚未刷新；醒目标记陈旧，不作为未经复核的当前完整事实。 |
| 3 | EXPIRED | 超过有效期，或来源代次/有效性不可接受；仅作标明时点的历史参考，重验并发布后方可恢复当前使用。 |
| 4 | UNKNOWN | 从未验证，或缺少来源、时间、证据，或验证失败；不得声称新鲜。 |

如来源有可验证的修订号或事件序列，应记录该值。不可比较时明确标为无法比较；不得由本地产生时间推断来源未变。

### 3.2 刷新 SLA

每个范围登记责任方、周期、最大允许滞后、刷新触发条件及失效处理。未另行规定时采用以下默认上限：

| 变更特征 | 默认刷新 SLA | 事件触发 |
|---|---:|---|
| 高频变化或影响访问控制/关键运行决策 | 24 小时 | 权限、身份、权威源或重大状态变化后立即刷新或标陈旧 |
| 常规业务或项目索引 | 7 天 | 创建、变更、迁移、退役事件后一个工作日内刷新 |
| 稳定参考目录 | 30 天 | 结构、责任方、Schema 或来源变更后刷新 |

责任方可设更严格 SLA。放宽默认值须记录理由、影响、批准者和复核日期；更严格的法律、合同、业务或安全要求优先。持续未达 SLA 时升级并保留失败记录，不得通过改写时间戳伪造新鲜度。

### 3.3 陈旧标记与过期清单

每个发布索引至少记录生成时间、最后验证时间、下次刷新期限、新鲜度、来源修订（若有）、陈旧起始时间（适用时）、验证结果、责任方和原因。进入 STALE 或 EXPIRED 时记录发现时间、影响范围及计划动作。生成时间不得冒充验证时间。

过期清单应从当前入口撤下或加醒目标识，并按保留规则留存为历史代次。来源核对、完整性与 Schema 验证、冲突处置和发布审批均完成前，不得恢复为当前清单。刷新时不得将旧清单未出现的对象直接解释为已删除；应区分确认移除、迁出、暂不可见、权限改变和漏采。缺少证据时标记 UNRESOLVED_HOLD。

## 4. 重建与发布协议

### 4.1 权限与并发 Agent

仅范围责任方、登记的重建维护者或其明确委派者可批准并发布新代次。执行者只可读取当前任务已授权的来源；重建本身不扩大访问或写入权限。并行 Agent 默认只读已发布代次；获准的并行工作可生成独立候选或审查意见，不得同时覆盖当前代次或发布指针。

发布前，维护者须取得登记的跨进程事务锁/租约或等效串行化机制，并在锁内重新读取当前代次、来源修订、状态和待合并变更。通过代次比较（CAS）拒绝基于旧基线的发布。锁缺失、超时或归属不明时失败关闭；不得绕锁写入。

### 4.2 原子重建与验证

在独立暂存代次生成候选，不得边生成边改写正在服务的索引。最低流程：

1. 记录稳定操作标识、基线代次、授权来源及修订、范围、执行者、规则/工具版本和计划。
2. 按既定规则读取并生成候选，保留来源引用；未知项不得静默丢弃或合并。
3. 验证 Schema、必需字段、稳定标识唯一性、引用、范围/权限约束、完整性证据、差异及陈旧项处置。异常变化须解释；示例不得使用真实清单计数。
4. 由有权维护者审阅差异和验证报告。未决冲突、未解释的重大差异、验证失败或授权不明时禁止发布。
5. 通过验证和审批后，在单一发布事务中原子切换当前代次/权威引用并记录结果。读者只能看到完整旧代次或完整新代次。

优先使用存储系统的事务或原子替换；不支持时使用不可变版本化代次和受控单一指针，并验证指针更新原子性。不得先删除旧索引再写新索引。

### 4.3 失败回退与旧清单

生成、校验、审批或切换失败时，旧有效代次保持不变；记录失败阶段、错误类别、候选引用和副作用状态。无法确认切换结果时标为 OUTCOME_UNKNOWN，先核验真实指针与代次，不盲目重试覆盖。

切换后发现缺陷时，由有权维护者通过新的受控事务回切至最后一个已验证代次，或发布修复代次；记录原因、目标代次、审批和验证。旧清单及其证据不可覆盖或就地改写，应按保留规则作为不可变历史代次保存。回退不得抹去发布和审计记录。

## 5. Lifecycle 与删除语义

生命周期、隐私分类、权威角色、物理位置和删除许可是不同维度。生命周期值须与适用 Schema 一致；本仓库现有索引记录 Schema 的 lifecycle 枚举包含 active、working、reference、archive、rebuildable、hold、retired、unknown，并未定义 tombstone。需要 tombstone 时，须先通过新 Schema 版本或兼容的独立生命周期事件明确数据契约，不得直接写入不合规值。

| 生命周期 | 语义 |
|---|---|
| active | 当前纳入维护或提供服务。仅经登记的权威源/验证发布物承担相应当前权威角色。 |
| reference | 只读查阅或依赖引用；不保证当前、完整或持续维护。 |
| archive | 按时间点封存的历史记录/代次；保留来源、时间、完整性和保留信息，不静默改作当前版本。 |
| retired | 停止维护或使用，不再常规变更；注明时间、原因及替代项（若有）。 |
| tombstone | 逻辑删除标记，保留稳定标识、时间、原因类别、授权与证据引用、替代项和限制；不等于保留原内容，也不证明已物理销毁。 |

活动索引移除、逻辑删除（tombstone）和物理销毁是不同操作。活动索引中缺席不证明源对象不存在；物理销毁须有明确范围授权、责任方批准、保留/法律保全核验、恢复风险评估和可审计结果。法律保全有效期间不得销毁。销毁受限内容后，仅留存获准的最小 tombstone 和不含敏感值的审计证据；须分别处置备份及衍生副本，不得假定它们已随主件销毁。

状态转换记录前态、后态、生效时间、操作者、批准依据、原因、关联代次和证据引用。用途或归属未明时保持 UNRESOLVED_HOLD；不得仅因时间久远自动退役、逻辑删除或销毁。

## 6. Retention、法律保全与审计证据

为索引、来源引用、快照、候选、日志和备份分别登记责任方、保留类别、期限、处置规则、隐私分类和适用依据。期限遵守适用法律、合同、业务记录要求及组织政策中更严格者；无法判定时暂停销毁并升级。

法律保全须记录范围、保全负责人、授权来源、生效时间、复核/解除条件，以及受影响的副本、衍生物和备份。保全有效期间，冻结相关的常规删除、过期清理、覆盖和破坏证据的转换。解除须有可核验授权并留存记录。法律保全限制处置，不自动授予读取或披露权限。

审计证据至少包含稳定操作标识、时间、操作者/角色、批准范围、目标代次、来源与修订引用、Schema $id/版本、规则版本、验证结果、差异摘要、切换/回退结果和证据引用；适用时包含内容摘要。使用受控访问和追加式或等效防篡改留存。日志、示例及公开索引不得含凭据、秘密值、敏感正文或不必要的个人数据。审计证据本身也受保留和法律保全约束。

## 7. Schema 身份、版本与迁移

### 7.1 $id 与版本

每个 Schema 使用稳定且唯一的 $id 识别其身份，不能依赖临时文件名、机器位置或会变化的发布地址。$schema 声明 JSON Schema 方言，不等同于业务 Schema 版本。每份索引记录使用的 $id 和确切版本。合成标识示例：urn:example:governance:index-record:v1。

一经发布，$id 与版本组合的既有含义不可改变，已弃用的 $id 不得复用，已发布版本不得作破坏性修改。版本应明确记录并遵循仓库约定；若无既定约定，采用语义版本：兼容性新增升次版本，破坏性变更升主版本，纯说明修正可升修订版本。验证器/约束版本或可审计的验证方法须可追溯。

### 7.2 弃用与兼容窗口

弃用公告应给出弃用标志、替代 $id/版本、理由、生效时间、支持终止时间、责任方和迁移说明。弃用不意味着立即删除历史数据或验证证据。紧急安全/合规变更可缩短窗口，但须记录批准和影响。新增字段须说明默认值、空值规则和消费者兼容性；不得假设旧消费者会忽略未知字段。破坏性变更须发布新主版本并说明映射与信息损失。

### 7.3 迁移策略

迁移由数据/索引责任方批准，在独立候选代次运行可重复、可审阅的转换。记录源/目标 $id 与版本、程序版本/摘要、输入代次、时间、映射规则、未知值处理、损失/新增/冲突摘要、验证报告和回滚引用。先进行只读盘点或试运行；验证完整性、引用、语义不变量和新旧 Schema 合规性后，审批并原子发布。

若采用双读/双写过渡，必须规定唯一写入权威、同步方向、冲突裁决和结束条件；不得把两个版本含糊地宣称为同一范围的权威。失败时保留源代次和候选，回到最后一个已验证版本。迁移完成后按保留规则封存旧版与映射证据。

Schema 校验只证明记录符合声明的数据形状，不证明来源权威、范围/权限安全、内容正确、索引新鲜或迁移已获授权；这些事项须分别核验并留证。

## 8. 发布检查表

- [ ] 范围、责任方、权威引用和副本角色明确且可核验。
- [ ] 来源修订、生成/验证时间、新鲜度与 SLA 状态完整。
- [ ] 冲突、遗漏、删除候选及异常差异已解释或隔离。
- [ ] Schema $id/版本、验证结果和迁移状态明确。
- [ ] 并发锁/CAS、原子切换、失败回退和旧代次留存已核验。
- [ ] 生命周期、保留类别、法律保全和物理删除限制已检查。
- [ ] 审计证据充分，且未泄露秘密值或不必要的敏感内容。
